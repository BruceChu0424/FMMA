# FMMA Build Notes (Windows / Quartus 25.1)

This file records the non-obvious build fixes applied to get the
Quartus/Qsys flow working on this machine, so the knowledge is not
lost. Everything here was needed because the installed Quartus
25.1std **SC Lite Edition** ships without the HPS EMIF/UniPHY
generation stack, and the WSL-based Nios II shell had a detection
bug.

## 1. Nios II Command Shell (WSL detection bug, FIXED)

`D:\Software\nios2eds\nios2_command_shell.sh` detected WSL with
`grep -q Microsoft /proc/version`. WSL2 kernels report
`microsoft-standard-WSL2` in **lowercase**, so the check failed and
the shell put a non-existent Linux toolchain directory on `PATH`
(`H-i686-pc-linux-gnu/bin`). Sequencer builds then died with
`make: not found` / `uniphy_mcc.exe: child process exited
abnormally`.

Fix applied:

* `nios2_command_shell.sh`: the grep is now case-insensitive
  (`grep -qi microsoft`).
* `D:\Software\nios2eds\bin\gnu\H-x86_64-mingw32\bin\make` (no
  extension): small sh shim that execs `make.exe` next to it, so a
  bare `make` resolves in the WSL-side PATH.
* `Nios II Command Shell.bat` was replaced with a native Windows
  version (original kept as `Nios II Command Shell.bat.orig`) that
  sets `QUARTUS_ROOTDIR`/`SOPC_KIT_NIOS2` and prepends
  `nios2eds`/`quartus`/`Git\usr\bin` to `PATH`. This avoids the
  WSL interop layer entirely for `qsys-generate`'s sequencer build.

With these fixes `qsys-generate` runs its sequencer `make` step
natively; only the EMIF IP issue below still stops full generation.

## 2. Missing EMIF/UniPHY IP in this Quartus install

`qsys-generate --synthesis=VERILOG Software\HPSfgpa2.qsys` stops in
`generate_hps_sdram.tcl` because the EMIF IP tree
(`quartus/ip/...`, `quartus/common/ip/altera/*emif*`,
sequencer templates `ac_rom.s`/`inst_rom.s`) is absent from this
installation. A complete Quartus Standard install regenerates
everything.

Four generated/library files that a complete generation would have
written into `Software/HPSfgpa2/synthesis/submodules/` were
therefore taken from a public mirror of Qsys output
(aekanman/FPGA-video-decoder) and are wired in via `HFTTop.qsf`:

| File | Role | Compatibility |
|------|------|---------------|
| `altera_mem_if_hard_memory_controller_top_cyclonev.sv` | hard DDR controller wrapper | port list checked against the `c0` instantiation in `hps_sdram.v` (169/169 ports match) |
| `altera_mem_if_oct_cyclonev.sv` | OCT calibration wrapper | exact port + parameter match |
| `altera_mem_if_dll_cyclonev.sv` | DLL wrapper | exact port + parameter match |
| `HPSfgpa2_mm_interconnect_0_avalon_st_adapter_error_adapter_0.sv` | Avalon-ST error adapter (renamed from the mirror, identical generation parameters: 34-bit data, no in-error, 1-bit out-error) | exact |

**If you regenerate the Qsys system on a machine with the full IP
stack, delete these four `set_global_assignment` lines from
`HFTTop.qsf` first** (the QIP will then provide its own copies and
duplicate definitions would collide).

## 3. Sequencer ROM hex files

`hps_sdram_p0.sdc` references `hps_AC_ROM.hex` / `hps_inst_ROM.hex`
at the project root (generated by `uniphy_mcc` from the DDR3
parameters). They are not in the repository. Without them Quartus
warns (`Critical Warning 127003`) and inits the ROMs to zero. DDR
calibration on this board is owned by the HPS preloader (the board
boots Linux from the SD image regardless), so the compile is not
blocked. The same warning exists for
`C:/intelFPGA_lite/ECE 3710/ECE3710_Project/Mif4.mif` - a leftover
init-file path from the original ECE 3710 machine; zero-init is the
desired power-up state for the shared RAM anyway.

## 4. HPS DDR3 pin I/O standards (Fitter error 174068/174052, FIXED)

The first fit attempt failed with 363 errors of the type *"output
buffer atom ... has port SERIESTERMINATIONCONTROL[0] connected, but
does not use calibrated on-chip termination"* and *"I/O HPS_DDR3_DQ[n]
has dynamic termination control connected, but does not use parallel
termination"*.

Cause: no I/O standard assignments existed for the HPS DDR3 pins, so
they defaulted to 2.5 V — a standard without calibrated OCT, while
the generated PHY connects the OCT calibration chain to every pad.

Fix: `HFTTop.qsf` now carries the `__hps_sdram_p0` assignment block
that a normal Qsys generation writes into the project (SSTL-15
CLASS I on single-ended pins, DIFFERENTIAL 1.5-V SSTL CLASS I on
CK/DQS, calibrated 50-ohm series/parallel termination on DQ/DQS/DM,
maximum drive on address/control). The block was adapted from a
public DE1-SoC project qsf to this system's widths (DQ[7:0], one
DQS pair, one DM, ADDR[12:0]).

## 5. QIP choice

`Software/HPSfgpa2.qip` (project root of Software/) is a **stale**
artifact with paths from an old directory layout. The real,
generated QIP is `Software/HPSfgpa2/synthesis/HPSfgpa2.qip` - that
is the one `HFTTop.qsf` references.

## 6. Command-line build

```
cd D:\Projects\OrCAD\FMMA
D:\Software\quartus\bin64\quartus_map.exe HFTTop     # analysis + synthesis
D:\Software\quartus\bin64\quartus_sh.exe --flow compile HFTTop
```

Programming file: `output_files/HFTTop.sof` (program via the
Quartus Programmer, JTAG, DE1-SoC).

**Result (2026-09-11):** full flow passes. Synthesis 0 errors;
fitter 0 errors; timing all met (worst setup slack +2.55 ns at
50 MHz, hold +0.143 ns); `HFTTop.sof` generated. Utilization:
1,652 / 32,070 ALMs (5 %), 1,121 registers, 4 M10K blocks (the
shared RAM), 2 DSPs (the CPU's MUL).

## 7. Simulation (no Questa license on this machine)

Icarus Verilog 12 was installed via winget
(`winget install Icarus.Verilog`). The full-chain testbench:

```
cd Testbenches
iverilog -g2005 -o tb_HFTTop.vvp ..\Software\HFTtop.v ..\Code\PC.v ^
  ..\Code\IR ..\Code\FR ..\Code\registerFinal ..\Code\MUX16to1 ^
  ..\Code\MUX2to1 ..\Code\ALUFinal ..\Code\FSMTrial ..\Code\disp ^
  ..\Code\Encoder4to16 ..\Code\decoder.v HPSfgpa2_stub.v tb_HFTTop.v
vvp tb_HFTTop.vvp
```

`HPSfgpa2_stub.v` is a behavioural model of the Qsys system
(dual-port RAM + registered slave port). Expected result: 8/8 PASS.
